## Goals vs. Non-Goals

The accepted context is the learner setting, authorization for review and planning-document reconciliation, and preservation of content, languages, routes and interface. The proposed goal is a small, reviewable improvement experiment that retains concise reference use and makes independent reasoning observable. Core questions should remain visible, solutions available after an attempt, and optional practice discoverable by purpose. Repeated examples should retain distinct reasoning roles.

This is not a new syllabus, a uniform lesson template, a course-wide rewrite commitment or a new learning platform. ## Key Decisions & Staging for Next Steps

**1. Draft the smallest testable tranche before code.** Prepare three English before/after pilot packages, a draft overview correction, entry checks and only indispensable adjacent bridges. Pilot A clarifies rule, permitted input and resulting statement; define a predicate as a condition evaluated at an allowed input, without requiring changing truth values. Supply short readings of unfamiliar set notation rather than another introductory chapter. Pilot B tests witness dependence on a complete unfamiliar numerical relation. Pilot C tests a changed constant/eventual-constant proof and the invalid choice `N=n+1`. The present core permits thresholds independent of tolerance. Assess reciprocal threshold construction and a written `2/n` transfer separately as optional extensions with their extra arithmetic facts supplied; add no model for that written task. Local pilot results do not establish that the entire beginner route works.

**2. Attach a short reasoning rubric and response to failure.** For predicates, check rule/input/statement and justification. For quantifiers, check complete domains, required witnesses and exclusion of all shared candidates. For convergence, check arbitrary positive tolerance, a natural threshold chosen before the test index, strict boundaries and every-tail-index reasoning. Record unaided, hinted and solution-seen attempts. A missing prerequisite prompts a local reminder or link; an omitted proof obligation prompts revision of that reasoning step. Interpret optional algebra errors separately. These checks guide edits and self-checking rather than generating mastery scores.

**3. Bound presentation ownership and preservation before implementation.** A presentation should own one coherent question, initial state, actions, outputs and reset behavior, with equivalent meaning in EN/DE/ES and a useful static view. Exact APIs can wait. Map relocated tasks by original identity, domain, assumptions, hint, solution and old fragments to active destinations. Review donor and recipient lessons as well as nominal pilots. Keep frozen historical evidence; create actual-version preservation evidence. Restore all affected content, presentation, compatibility and records together if a pilot is withdrawn. These are later-design requirements, not missing code specifications for this brief.

**4. Bound the first investment and expose scheduling uncertainty.** Stop the first work package at the three draft comparisons, reference arguments, prerequisite bridges and observation sheets. Review those before component work. Implementation of three retained pilots touches at least nine locale lessons, plus explicitly scoped donor/recipient pages, shared copy and evidence. Separate drafting, localization, mathematical/semantic review, preservation work and learner checking. Re-scope any pilot that needs another topic, a new engine or broad prerequisite rewrites. Human review availability, learner access, reliable effort bands and calendar dates remain open; settle them for the retained design instead of inventing a schedule. Estimate wider work from pilot costs.

**5. Make expansion an explicit decision.** With learners, use comparable unfamiliar tasks and revisit changed cases where practical; investigate unresolved misconceptions before extending a pattern. Without learners, record an editorially reviewed but unvalidated pilot and permit only bounded source-supported corrections. Then choose retain, revise, expand the supported pattern or propose broader revision. Build/browser verification establishes technical behavior; semantic review establishes preservation evidence; neither demonstrates learning effectiveness or expert mathematical/translation certification. Later proposal revisions are the root's reconciliation and are not independently re-reviewed by this run.
